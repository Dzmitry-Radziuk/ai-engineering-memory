# Подключение Codex

MCP SDK запускается как локальный процесс через stdio. Установите проект в виртуальное окружение командой `python -m pip install -e .`.

Для изолированного запуска можно задать `AI_MEMORY_DB` в окружении MCP сервера; путь должен указывать на локальную SQLite-базу.
Привилегированные изменения знаний и Skills не зарегистрированы как MCP-инструменты. Решения по кандидатам знаний выполняются интерактивно через `ai-memory knowledge review`; предложения Skills одобряются или отклоняются, а версии откатываются только локальными CLI-командами `ai-memory admin skill`. Эти действия требуют `AI_MEMORY_MAINTAINER` и точного подтверждения в интерактивном терминале. Подробные команды приведены в README.

Добавьте сервер в пользовательский `config.toml` вручную, сохраняя существующие записи:

```toml
[mcp_servers.ai_engineering_memory]
command = "D:\\Projects\\ai-engineering-memory\\.venv\\Scripts\\python.exe"
args = ["-m", "ai_engineering_memory.cli", "mcp", "serve"]
cwd = "D:\\Projects\\ai-engineering-memory"
```

В CLI Codex тот же блок обычно размещается в `%USERPROFILE%\.codex\config.toml`; расширение VS Code использует конфигурацию Codex текущего профиля. Не копируйте пример вслепую поверх существующего файла. После сохранения перезапустите Codex и проверьте список инструментов чтения, создания кандидатов, работы с предложениями Skills и learning. Утверждение/отклонение знаний и Skills, а также откат Skills не публикуются как MCP-инструменты; решения по знаниям принимайте через `ai-memory knowledge review`.

Проверка подключения считается завершённой только после успешного перечисления инструментов и безопасного `memory_search` на тестовой базе. В этой реализации MCP-процесс локален, но реальное подключение Codex здесь не проверялось. Claude Code, Cursor и пользовательские агенты должны запускать такой же stdio entry point с настройками своего клиента; они не проверялись.

## Локальный плагин в меню @ приложения ChatGPT/Codex

В проекте есть repo-scoped marketplace `.agents/plugins/marketplace.json` и плагин `plugins/ai-engineering-memory` со Skill `ai-memory`. В `plugin.json` явно задано `extensions.com.openai.hooks = {}`, поэтому сам plugin hooks не регистрирует. Hooks `UserPromptSubmit` и `Stop` отдельно устанавливаются в пользовательский профиль командой `ai-memory hooks install`; это единственный штатный способ их активировать и избежать дублирующих обработчиков. Prompt hook использует уже подключённый MCP-сервер `ai_engineering_memory`; отдельный сервер или копия базы не создаются.

### Установка и вызов

Перед регистрацией или установкой marketplace сохраните пользовательский конфиг Codex:

```powershell
$config = Join-Path $env:USERPROFILE '.codex\config.toml'
$backup = "$config.backup-$(Get-Date -Format yyyyMMdd-HHmmss)"
Copy-Item -LiteralPath $config -Destination $backup
```

Из корня этого проекта добавьте локальный marketplace и установите плагин официальными командами:

```powershell
codex.cmd plugin marketplace add 'D:\Projects\ai-engineering-memory'
codex.cmd plugin add 'ai-engineering-memory@ai-engineering-memory-local'
codex.cmd plugin marketplace list
codex.cmd plugin list --marketplace ai-engineering-memory-local
```

Если плагин уже отображается как `installed: true`, но версия отличается от `plugin.json`, повторите установку из обновлённого marketplace. Затем:

1. Откройте этот репозиторий как рабочую папку в приложении ChatGPT/Codex Desktop для Windows и перезапустите приложение после обновления файлов.
2. Проверьте план установки командой `.venv\Scripts\ai-memory.exe hooks install --dry-run`: результат перечисляет только названия изменяемых полей и не показывает их старые значения. Затем при необходимости запустите `.venv\Scripts\ai-memory.exe hooks install`. Команда объединяет только `UserPromptSubmit` и `Stop`, задаёт каждому 5-секундный таймаут, сохраняет остальные настройки и перед изменением существующего `hooks.json` создаёт резервную копию. Для другого профиля передайте `--config <путь>`. В `/hooks` проверьте оба определения и подтвердите trust только для этих hooks. Codex пропускает недоверенный hook.
3. Создайте новый чат в репозитории и отправьте обычный рабочий запрос. Командный `UserPromptSubmit` hook читает JSON-событие Codex и ищет до пяти результатов только со статусом `approved` в `global` и текущем проекте. Он резервирует до трёх мест под текущий проект, чтобы совпадения из `global` не вытеснили проектные правила; свободные места заполняются результатами из другой области. Записи передаются как JSON со значением `scope=project` или `scope=global` внутри помеченного блока недоверенных справочных данных. Hook не читает transcript целиком и не ищет кандидаты автоматически. При пустом результате hook не добавляет память.
4. Для ручного обзора вызовите `@AI Engineering Memory` и спросите обзор или конкретную запись.

Codex CLI и приложение используют пользовательский профиль Codex. Установка marketplace/plugin обновляет `config.toml`, а команда `hooks install` обновляет `hooks.json`. Резервная копия `hooks.json` позволяет восстановить файл целиком; команды отката ниже убирают только marketplace/plugin и не удаляют записи hooks автоматически.

Skill можно вызвать как `$ai-memory` в Codex CLI или через `@AI Engineering Memory` в Desktop. Для обзора Skill вызывает `memory_overview`; для инженерных решений — `memory_search` с `status="approved"`; кандидаты включаются только по явному запросу. `namespace`, `category` и `status` — разные точные фильтры. Skill никогда не меняет статус автоматически. Явное добавление знаний выполняется через `memory_add_candidate`, а обновления Skills лишь предлагаются через `skills_propose_update`. Перед решением по предложению вызовите `skills_get_proposal`: он показывает предлагаемый и текущий тексты, оба считайте недоверенными. Для автоматического обучения текущая Codex-модель анализирует завершённую инженерную работу и при наличии переносимого урока вызывает `learning_add_candidate` с ID успешной локальной проверки; результат остаётся candidate в namespace проекта.

### Проверка и обучение

Hook возвращает протокольный JSON в UTF-8 через `stdout`, независимо от системной кодовой страницы Windows.

Текстовый `AI_MEMORY_TASK_VERIFIED` больше не считается доказательством. `Stop` остаётся быстрым: он не создаёт learning event ни по завершению хода, ни по маркеру. Для независимой локальной фиксации используйте CLI и запускайте проверку прямо через него:

```powershell
.venv\Scripts\ai-memory.exe learning verify --task-id task-123 --summary "Harden retry handling" --cwd D:\Projects\sample -- python -m pytest -q
.venv\Scripts\ai-memory.exe learning status
.venv\Scripts\ai-memory.exe learning list
.venv\Scripts\ai-memory.exe learning process
```

Verify запускает argv без shell, сохраняет код возврата, время, digest команды и stdout/stderr, но не сохраняет исходную команду, содержимое вывода или абсолютный cwd. Перед запуском проверяет, что пути `--changed-file` существуют как файлы внутри `cwd`; symlink/junction за пределы проекта отклоняется. Эти ссылки переданы вызывающим и проверены на существование, но это не доказывает, что файлы были изменены или проверены указанной командой. Только exit code 0 создаёт событие `pending_analysis`. Это подтверждает запуск команды, но само по себе не доказывает качество проверки. Нулевой код без конкретной проверочной команды не является достаточным основанием.

`learning process` с opt-in localhost Ollama сохранён только для старых ожидающих событий и не нужен обычному циклу Codex. В штатном потоке `UserPromptSubmit` добавляет краткую инструкцию для инженерных запросов. Если задача или правила проекта требуют реальной проверки, текущая модель Codex может запустить её один раз через `ai-memory learning verify` с обязательными `--task-id`, `--summary`, `--cwd` и фактической командой после `--`; дополнительная проверка только ради памяти не запускается. Без подходящей успешной проверки или переносимого урока candidate не создаётся. Затем модель может вызвать `learning_add_candidate`. Это best-effort: hook не запускает модель, эвристика может пропустить запрос, а модель может не вызвать MCP. MCP повторно проверяет успешный `verification_id`, выводит project namespace из события, валидирует приватные данные и ссылки, исключает дубли и создаёт только `candidate`. Ссылки `file:<relative-path>` принимаются только когда Git показывает путь изменённым, staged или новым; verifier сохраняет только такие переданные пути. Это не доказывает, что указанная команда проверила файл. Ошибки не должны блокировать основную задачу. Skills и approved-записи автоматически не меняются.

Результаты обоих командных hooks записываются в `%LOCALAPPDATA%\AIEngineeringMemory\hooks.jsonl` (либо в `PLUGIN_DATA\hooks.jsonl`, если Codex передал эту переменную). Журнал содержит timestamp, событие, источник, статус, длительность, количество результатов и тип ошибки; для `UserPromptSubmit` также сохраняется только булев признак, добавлена ли обучающая инструкция. Размер ограничен ротацией. Переменная `AI_MEMORY_HOOK_LOG` позволяет направить журнал в тестовое место. Prompt, ответы, содержимое инструкции, файловые пути и raw tool output в журнал не записываются.

Для безопасной проверки локальной установки используйте `.venv\Scripts\ai-memory.exe doctor`. Команда только читает SQLite, `%USERPROFILE%\.codex\hooks.json` (или `%CODEX_HOME%\hooks.json`), `config.toml` и хвост журнала; она не вызывает hook или MCP-сервер и не меняет эти файлы. Поле `memory_mcp` проверяет регистрацию `ai_engineering_memory`, доступность launcher, ожидаемую форму `mcp serve` и существование абсолютного `AI_MEMORY_PROJECT_ROOT`, если он указан; сам путь не выводится. Абсолютные локальные пути по умолчанию скрыты в отчётах; локально показать их можно с `doctor --show-paths`. Если корень не задан, процесс использует свой рабочий каталог. Статус `configured` и `runtime_verified=false` означают, что сервер не запускался. Опциональный `doctor --probe-mcp` запускает распознанный MCP-сервер, получает список инструментов и вызывает только read-only `memory_search` с пустой временной БД: переменная `AI_MEMORY_DB` в дочернем процессе принудительно перенаправляется во временную папку. Это доказывает доступность реального tool call в процессе `doctor`, но не доступ к основной БД и не работу сервера внутри Codex. В разделе hooks показаны количество регистраций, доступность команд, ожидаемый 5-секундный таймаут и актуальность `statusMessage`. Неверный таймаут или повторная регистрация hook-а переводит проверку в `warning`. Отличие только `statusMessage` показывается отдельно: оно меняет текст уведомления, но не мешает запуску hook-а. Перед изменением конфигурации просмотрите dry-run командой `.venv\Scripts\ai-memory.exe hooks install --dry-run`. Повторная регистрация `UserPromptSubmit` или `Stop` также переводит проверку в `warning`, поскольку один prompt может обрабатываться несколько раз. Поле `launcher_matches_current_interpreter` сравнивает только путь executable hook-команды с Python, на котором запущен `doctor`; команда не исполняется, и это сравнение не подтверждает импорт модуля или фактический запуск Codex. Одна регистрация подтверждает только конфигурацию, а не фактический запуск Codex; исполнение подтверждается свежими записями в диагностическом журнале. Сравнение версии hook с последней записью журнала проверяет только версию последнего наблюдавшегося запуска: несовпадение без нового события не доказывает, что текущая конфигурация устарела. Последняя ошибка hook или повреждённые строки журнала переводят проверку в `warning`; исторические ошибки остаются видны в счётчике, но не маскируют успешный более поздний запуск того же события.

MCP ограничивает поиск, обзор, чтение, запись и проверенные learning events значениями `global` и namespace одного проекта. Для закрепления проекта задайте `AI_MEMORY_PROJECT_ROOT` абсолютным путём в окружении MCP-процесса; без него используется рабочий каталог процесса или поле `cwd` в конфигурации сервера. Область фиксирована для процесса: при смене workspace перезапустите MCP с корнем нового проекта. Codex также поддерживает отдельную `.codex/config.toml` для доверенного проекта; `.venv\Scripts\ai-memory.exe project-config --cwd <путь>` печатает блок для неё, не изменяя файлы. `doctor --cwd <путь>` сравнивает закреплённый корень или абсолютный `cwd` сервера с проверяемым проектом и сообщает о несовпадении, не раскрывая пути. Если `cwd` относительный, doctor считает область непроверенной; `doctor --probe-mcp` пропускает запуск при несовпадении или непроверенной области. Параметр `namespace` от модели не может расширить эту область. Hook `UserPromptSubmit` вычисляет namespace от корня `.git`, содержащего переданный Codex `cwd`; вне Git используется сам `cwd`. Поэтому запросы из подпапок репозитория совпадают с namespace закреплённого корня MCP.

После изменения marketplace-плагина обновите его источник в локальном marketplace и перезапустите приложение ChatGPT/Codex, чтобы установленная копия перечитала Skill.

При выпуске локального изменения увеличьте `version` в `plugins/ai-engineering-memory/plugin.json`, затем из корня репозитория выполните `codex.cmd plugin add 'ai-engineering-memory@ai-engineering-memory-local'`. Новая версия устанавливается в отдельный каталог кэша, не удаляя предыдущие знания или версии Skills. Проверьте `codex.cmd plugin list --marketplace ai-engineering-memory-local --json` и перезапустите приложение, чтобы оно загрузило новую установленную версию. Обновление локального файла manifest не обновляет уже установленную user-level копию автоматически.

### Что поддерживается и ограничения

- MCP-сервер — локальный stdio-процесс, который предоставляет инструменты. Плагин — устанавливаемая упаковка возможностей и инструкций. Skill — инструкции для последовательного вызова инструментов.
- Официальный локальный marketplace поддерживается desktop-приложением ChatGPT/Codex и может быть repo-scoped. ChatGPT web не подключается напрямую к локальному MCP-серверу; для web нужен удалённый сервер или поддерживаемый OpenAI Secure MCP Tunnel, что здесь не настраивается.
- Плагин использует глобальную настройку MCP текущего профиля. Если сервер недоступен в приложении, проверьте `codex.cmd mcp list` и существующий блок `[mcp_servers.ai_engineering_memory]`; не добавляйте второй блок сервера в пакет.
- В этой конфигурации hooks регистрируются в user-level `%USERPROFILE%\.codex\hooks.json`, поскольку CLI не показывал bundled hooks даже при включённом плагине. Пакетная копия в manifest отключена во избежание двойного запуска. Hooks требуют отдельного доверия в клиенте. Реальный retrieval следует проверить по теме, для которой есть approved-знание. Наличие файла hook само по себе не подтверждает исполнение; сверяйте журнал запусков. При изменении пользовательской регистрации или тела hook клиент может потребовать повторного доверия; эта итерация пользовательские hooks/trust не меняла.
- В VS Code расширение OpenAI использует конфигурацию Codex текущего профиля. Repo marketplace не означает, что пользовательский плагин уже установлен в приложении.

### Откат

Удалите плагин и marketplace из пользовательской конфигурации:

```powershell
codex.cmd plugin remove 'ai-engineering-memory@ai-engineering-memory-local'
codex.cmd plugin marketplace remove 'ai-engineering-memory-local'
```

Затем при необходимости удалите только каталог `plugins/ai-engineering-memory` и запись плагина из `.agents/plugins/marketplace.json`. Глобальная конфигурация MCP и база данных при этом не затрагиваются. Полное восстановление резервной копии `config.toml` заменит весь текущий файл, поэтому используйте его только если после копирования не появилось других нужных настроек. Отключение или удаление плагина прекращает автоматический поиск; предыдущую версию plugin cache можно оставить как резерв.
