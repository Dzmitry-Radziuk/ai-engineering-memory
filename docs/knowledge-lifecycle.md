# Жизненный цикл знаний

Новое знание всегда получает статус `candidate`. Только maintainer может явно изменить этот статус. Автоматическая обработка learning events не утверждает записи и не обновляет активные Skills.

Статусы знаний: `candidate` → `approved`, `rejected` или `deprecated`. Обычный поиск по умолчанию возвращает только `approved`. `memory_overview` показывает все состояния и namespaces.

## Автоматический контекст Codex

`UserPromptSubmit` ищет до пяти применимых `approved` записей в `global` и точном namespace текущего проекта. В prompt-поиске сначала идут записи, совпавшие со всеми значимыми словами запроса; свободные места заполняются частичными совпадениями. В FTS5 их порядок определяет релевантность FTS, а в резервном LIKE-поиске — число совпавших слов, совпадение в заголовке и затем дата обновления. Чтобы общие записи не вытесняли локальные, hook сначала резервирует до трёх мест для текущего проекта, затем заполняет остальные глобальными знаниями; свободные места заполняются результатами из другой области. Контекст содержит ограниченный JSON-массив с явным `scope` каждой записи; массив помечен как недоверенные справочные данные, а `<`, `>` и `&` в полях экранируются. Для Git-проекта namespace строится от корня репозитория, содержащего `cwd`; вне Git используется сам `cwd`. Поэтому подпапки одного репозитория используют общую память, а другие project namespaces и `candidate` не возвращаются. Hook fail-open: ошибка поиска не блокирует пользовательский запрос.

Для распознанных инженерных запросов hook также добавляет компактную инструкцию Codex: после фактической проверки оценить переносимость урока и при наличии вызвать `learning_add_candidate`. Общего глагола вроде «создай», «улучши» или `test` недостаточно: запрос должен содержать и технический контекст. Эвристика может пропустить задачу; Codex также может не последовать инструкции. Это best-effort, не обязательная транзакция для каждого хода.

## Доверенное событие проверки

Завершение хода и текст `AI_MEMORY_TASK_VERIFIED` сами по себе не доказывают прохождение проверки. `Stop` только записывает метаданные hook-а: `marker_present_unverified` означает, что маркер встретился в тексте ответа, а `no_marker_seen` — что он не встретился. Ни один результат не является доказательством запуска проверки и Stop не помещает событие в learning queue.

Для явного подтверждения запустите `ai-memory learning verify --task-id <id> --summary <summary> --cwd <project-root> -- <program> <args...>`. Команда запускает argv непосредственно, без shell, с ограниченным таймаутом. Только локально полученный exit code 0 создаёт `verification_records` и связанное событие `pending_analysis`; результат CLI сообщает `process_succeeded` и `verification_scope=process_exit_code_only`. Это подтверждает только успешное завершение процесса, не выполнение задачи и не прохождение тестов. Ненулевой exit code и таймаут сохраняют неуспешную попытку без постановки события в очередь. Если процесс не удалось запустить, сохраняются только метаданные попытки с `verification_type=command_launch`, `exit_code=-2` и `error_type=CommandLaunchError`; системный текст ошибки не сохраняется, событие в очередь не попадает.

Последние неуспешные попытки можно просмотреть командой `ai-memory learning attempts`; `--all` включает успешные, а `--limit` ограничивает выдачу (1–100). Список содержит только хеши ID проекта и проверки, task ID, тип запуска, exit code, время и статус доверия; сырые команды, вывод и абсолютные пути в нём отсутствуют. `ai-memory learning status` показывает агрегированные числа проверок отдельно от событий, ожидающих анализа. Для короткой сводки без JSON используйте `ai-memory learning status --human`; она отдельно поясняет Codex-native best-effort capture и ручной legacy-анализ.

Хранятся тип проверки, времена, exit code, обезличенный project ID и digest команды/вывода. Сырая команда, output, transcript и абсолютные пути не сохраняются. Verification доказывает только запуск указанного процесса с данным exit code; она не доказывает полноту или корректность самих тестов.

## Анализ Codex и candidate capture

После завершения безопасной проектной проверки модель текущего Codex-сеанса сама формулирует problem, root cause, solution, conditions, limitations, verification summary и confidence. Python не вызывает LLM. Если перенести нечего или доказательства недостаточны, candidate не создаётся.

`learning_add_candidate` принимает только точный `verification_id`, связанный с локальным trusted verifier и exit code 0. Namespace нельзя выбрать в аргументах: сервер получает `project:<sha256-prefix>` из проверенного события. Evidence должна содержать этот verification ID; ссылки `file:<relative-path>` допустимы только для переданных вызывающим файлов, которые существовали внутри проекта во время проверки. Это не доказывает, что файл был изменён или проверен командой. Tool ограничивает размеры и отказывает при секретоподобном контенте, неправильных ссылках, неуспешной/отсутствующей проверке и слишком коротком выводе.

В candidate отдельно указано, что серверный verifier подтвердил только exit code 0 и не оценивал релевантность или полноту команды. Переданная моделью `verification_summary` показывается как непроверенный комментарий, а в evidence та же граница повторяется. Это не позволяет принять пояснение модели за результат анализа verifier-а.

Межпроектное накопление сравнивает новые lessons с `candidate` и `approved` записями из project namespaces. Совпадение в текущем проекте или в другой копии того же Git origin считается дублем. Для решения о независимости используется версионированный SHA-256 fingerprint нормализованного origin; учётные данные, query, исходный URL и пути в fingerprint не попадают. Если у репозитория нет доступного `origin`, знание остаётся локальным кандидатом: разные пути не считаются доказательством независимости. Fingerprint старого формата также не поддерживает новое global-подтверждение. Уже сохранённые старые подтверждения не удаляются и не переписываются: `learning_get_corroboration` показывает их отдельным legacy-счётчиком, а число независимых подтверждений считает только новые отпечатки origin. При двух разных актуальных origin fingerprint ядро атомарно создаёт дополнительного `global` candidate и связывает его с локальными verifier evidence. Последующие независимые fingerprint добавляют corroboration через `learning_get_corroboration`. Эти данные подтверждают повторяемость, но не делают запись автоматически approved.

Дедупликация сравнивает `approved` и `candidate` в global и точном проекте. Точное повторное обращение на одном verification ID идемпотентно; похожий урок пропускается и фиксируется в `learning_event_audit`. Межпроектные candidates не участвуют в сравнении. Новое знание всегда остаётся `candidate`; инструмент не утверждает знания и не меняет Skills. Отклонение candidate через `learning withdraw` сохраняет причину в audit.

Для удобного обзора запустите `ai-memory knowledge review --cwd <project-root>`. Команда показывает только candidates общей памяти и указанного проекта вместе с доказательствами и количеством независимых отпечатков. Действие доступно только в интерактивном терминале; для утверждения или отклонения нужно ввести точный ID-команду. Отклонение требует причины, все изменения статуса записываются в audit. Список можно ограничить параметром `--limit`. Для чтения без интерактивного обзора используйте `ai-memory knowledge list --status candidate --namespace <project-namespace>`; MCP `learning_get_corroboration` также показывает подтверждения межпроектных записей. `learning process` и opt-in localhost Ollama оставлены для legacy очереди; они отключены по умолчанию и не нужны обычному циклу Codex.

## Фильтры и экспорт

| Фильтр | Пример | Назначение |
| --- | --- | --- |
| `namespace` | `global`, `project:0123...` | Точное пространство памяти |
| `category` | `ai_agents`, `backend` | Класс записи |
| `status` | `approved`, `candidate`, `deprecated`, `rejected` | Состояние записи |

Экспорт выдаёт только явно выбранные записи со статусом `approved` и `publishable=true`. Импорт создаёт новые кандидаты и не перезаписывает существующие знания.
